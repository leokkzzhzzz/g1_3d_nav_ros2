> Nav2 plan → twist_mux → `g1_write_node` → SDK `LocoClient::Move()` →

> software pipeline up to `/cmd_vel_out` but stopped short of motion

## Closed-loop verification

Result: **PASS** (goal-driven motion confirmed by operator visual
observation; `bt_navigator` reports `Goal succeeded` once G1 enters
`xy_goal_tolerance: 0.10` of the goal).

Evidence captured from `/tmp/nav2.log` after a single goal:
```
[bt_navigator] Begin navigating from current location (-0.80, 1.17) to (-0.76, 1.23)
[bt_navigator] Goal succeeded
```
plus `controller_server` continuously reporting `Passing new path to
controller.` at ~1 Hz throughout the run.

`grep -c base_footprint /tmp/nav2.log` = 0 — the D-009 fork's
`robot_base_frame: body` is in effect.

## What broke first, and how it was diagnosed

The first two `nav2_launch.sh` runs of the day flooded `/tmp/nav2.log`
with `frame "base_footprint" does not exist` at 2 Hz. Static checks
exonerated the obvious suspects:

| Check | Result |
|---|---|
| Host-side D-009 fork content | `robot_base_frame: body` in 4 places |
| Docker mount table | `host fork → install/share/.../nav2_params.yaml` |
| `docker exec ... cat` of mount target | Shows fork content (mount apparently delivered) |
| `ros2 pkg prefix g1_pkg` | Resolves to mount target's package prefix |
| `nav2.launch.py` yaml resolution | `get_package_share_directory('g1_pkg')` |
| `ReplaceString` substitutions | Only `<prefix>` and `<back_obstacle_layer>` — does not touch `body` |

After `docker stop 3d_nav_ros2 && docker start 3d_nav_ros2` followed
by a fresh `launch.sh + nav2_launch.sh`, `base_footprint` errors went
to **0** and the closed loop worked first try. Root cause not fully
established; tracked as Roadmap R-009. Working hypothesis: the bind
mount overlay is not always picked up by long-lived nav2 processes
across `nav2_launch.sh` restarts; a full container restart re-binds
cleanly.

## Findings worth keeping

- **MPPI closed-loop output drives G1 fine with botbrain defaults**
  (`vx_max: 0.35`, `min_x_velocity_threshold: 0.001`). The single-step
  dead-zone observed in R-003 closure (`vx=0.05` no motion, `vx=0.5`
  motion) does **not** apply to the closed-loop 20 Hz Twist stream Nav2
  drives. D-011 v3's "do not pre-emptively tune Nav2 velocity numbers"
  stance is validated.
- **`xy_goal_tolerance: 0.10`** is achievable on G1 — the recorded run
  ended at 4 cm from the goal (under tolerance) and `bt_navigator`
  fired `Goal succeeded`.
- **Continuous goal preemption is operator-visible as "G1 doesn't stop"**
  — when the operator clicks `2D Goal Pose` repeatedly, each click
  preempts the previous goal. G1 keeps walking because each preempted
  goal is replaced with a new one. This is correct Nav2 behaviour, not
  a bug.

## What still needs measurement (not done in this report)
